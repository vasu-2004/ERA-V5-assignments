1How many strategies, and what are they

The session states this explicitly — a student counted them live and the instructor confirmed: “we have been using around eight sections… this is a minimal set, maximal can set, this is the minimum that we have to do.” 8 strategies, applied in this fixed order (each stage's output is the next stage's input):

1Extract — pull real content out of raw HTML; drop nav/footer/cookie-banners/scriptsbs4
2Normalize — NFC, HTML-entity unescape, whitespace collapse, ghost-tag & license-header strip — Brahmic-safe (ZWNJ/ZWJ preserved)regex+unicodedata
3Language ID & validation — never trust the folder name; detect the real language per documentpy3langid
4Quality filter — Gopher/C4-style heuristics (mean word length, symbol ratio, stopwords, bullet/dup-line ratio)heuristic cascade
5Deduplication — near-duplicates, not just exact copies: shingle → hash → LSH bandMinHash+LSH
6PII scrub — emails, phones, IPs, usernames; keep public figures, drop private individualsregex+NER-heuristic
7Decontamination — nothing from a held-out benchmark may survive into trainingcanary + MinHash
8Manifest — source, license, contributor, script hash, shard hash, token/language counts per shardprovenance record

Also discussed in the session but not separate pipeline stages: MinHash/LSH mechanics (the how inside stage 5), synthetic rephrasing for low-resource languages, and canary-GUID leak detection (the mechanism inside stage 7) — folded into the stages above rather than counted twice.

4Other strategies/concerns cleaned up along the way

These weren't in the plan — they turned up while running the pipeline on real data, which is the actual point of doing this rather than just describing it.

Script ≠ language. Maithili and Hindi share the Devanagari script; a naive script/statistical check flagged real, correctly-labelled Maithili wiki text as "mislabelled" against Hindi. Dropping it would have repeated the exact low-resource-Indic mistake the session warns about. Fix: the drop-on-mismatch rule now applies only to the deliberately-constructed mislabel trap, not to source-verified content — disagreements on real data are recorded, not deleted.
One quality rule, two registers. A general-prose stopword-density threshold (tuned for news/Wikipedia) wrongly failed legitimate GSM8K math problems — word problems are naturally stopword-sparse (many names/numbers, few function words). Fix: a domain-specific floor for the math bucket, not a global loosening of the rule.
Bold markdown looked like a bullet list. **India** starts with *, so a naive "line starts with a bullet marker" check misfired on Wikipedia's own bolded lead sentence. Fix: require marker and trailing space, so **bold** and - item are no longer confused.
Decontamination over-flagged shared phrasing as leakage. A first pass flagged 37 GSM8K test questions as "contaminated" because they shared a common 10-word phrase (e.g. "how many...", "find the total amount") with a training document — but GSM8K problems reuse boilerplate reasoning sentences across unrelated questions; sharing a phrase isn't sharing an answer. Fix: require whole-document MinHash similarity, not any shared n-gram — result dropped to 0 genuine leaks, which is the correct answer for two disjoint official splits.
PII regexes don't belong on source code. Running email/phone/IP patterns over real .py files matched version strings and numeric literals, not personal data. Fix: PII scrubbing is scoped to prose buckets only — code gets license-header stripping instead, per the session's own point that different content needs different rules.
Fixed shingle size doesn't fit both a tweet and a novel. An 8-word shingle (tuned for full news articles, matching the session's own demo) under-measured similarity between short, reworded PR one-liners — a same-story reorder scored only 0.33 Jaccard. Fix: shingle size now scales down for short documents; still an honest partial catch (4/6, not 6/6) rather than a rigged one.
Language-ID noise on tiny fragments. Several one-line Wikipedia image captions (just a name + URL) were misclassified by py3langid as Latin, Indonesian, Javanese, German, Malay, Dutch, or Chinese — real evidence for the session's insistence on validating language ID rather than trusting one classifier's output on short text.
